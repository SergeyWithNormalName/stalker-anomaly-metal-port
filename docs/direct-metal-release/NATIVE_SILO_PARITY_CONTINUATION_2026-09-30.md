Медиана CPU encode уменьшилась с 47,793 до 35,595 мс; медиана indexed draws с 21 320 до 14 840; elapsed command buffer с 37,892 до 31,950 мс. Вложенные CPU интервалы и GPU elapsed нельзя складывать или трактовать как occupancy. Прогоны: `runs/r1-policy-off-01` и `runs/r1-policy-on-01` под `scratch/native-silo-parity-20260929/`.

Однокадровый join фактически показал причину: при OFF 59 статических родителей дали 354 захваченные записи; среди 285 реально нарисованных локальных shadow faces 222 принадлежали 37 статическим родителям, которые Windows с текущей настройкой не экспортирует. Отдельная проверка переключения игрового `r2_allow_r1_lights` внутри одного процесса вернула статические пакеты при включении; она записана в `runs/r1-policy-visual-toggle-01`.

## Почему победа над Windows пока не объявлена

Неизменённый установленный Windows `AnomalyDX11.exe` SHA-256 `c0bf73944e700425734d95b71f5c8fd201b669bac67d295357a141442103bdd3` падает до actor callback на пустом `CModelPool::Exists/Create` при попытках загрузить этот и другие save или начать новую игру в текущем Silo/WineCX 26.3.0. Для диагностики была сделана *только в scratch* приватная копия EXE SHA-256 `1a3ff9acbab231da7348ad61969d6e910d229233ae982b48a8e4e5a23b271c20`: 28 изменённых байт в двух диапазонах добавляют отказ для null/empty model query, сохраняя обычный путь nonempty. Оригинальный EXE, установленная GAMMA, моды и их источники не переписывались; такой binary patch не предназначен для распространения.

На приватной исправленной Windows-копии тот же save/camera/resolution/weather/настройки дали On-Glass 16,7909 и 15,7115 кадра/с в двух диагностических прогонах (`windows-emptyguard-canonical-01/02`); первый закончен harness timeout после измеренного окна, второй exit 0. Однако Silo достигает actor callback позже: игровой календарь во время окна около 08:19 вместо native 08:13, и видимые данные мира/AI могут различаться. Поэтому даже численно лучший native результат нельзя объявить честной победой над **неизменённой** Windows-версией в идентичных обстоятельствах. Прежние 32,10 Silo против 19,83/13,19 native из `WINDOWS_SILO_METAL_FRAME_BUDGET_2026-09-29.md` относятся к разным игровым состояниям и бинарникам; их нельзя использовать как прямую итоговую пару.

Чтобы проверить чувствительность этого вывода к часовому дрейфу, внешний профиль `matched_profile_calendar_0818.lua` через имеющийся в обеих версиях `level.change_game_time` сдвинул оба запуска только вперёд к минуте 08:18 *до* прогрева. В `runs/r1-final-calendar-0818-01` native пришёл к 08:18:38 из 08:11:38, Silo — к 08:18:01 из 08:17:01; оба затем выставили `w_clear2` и одинаковые параметры камеры/экрана. Измеренные интервалы календаря всё ещё разнятся примерно на 37 секунд. При этом **обычная native сборка дала On-Glass 25,2787 FPS, а приватная Windows/Silo — 29,8811 FPS**; callback 25,3463 против 33,3648. P99 интервала *показанных* кадров — 50,00 против 106,71 мс соответственно; native в этом окне ровнее при меньшем среднем FPS. Оба процесса завершились с кодом 0. Эта пара меняет направление численного результата: предшествующие 15–17 FPS Silo не были устойчивым ориентиром. Аудит `weather.csv` затем обнаружил, что одинаковое имя `w_clear2` скрывало разные реальные wind/ambient/hemi/fog/far значения. Причина по исходникам: старый Windows `set_weather_weight` меняет границы blend, но внешний профиль ставил паузу до следующего `Environment::OnFrame`; native WIP применяет blend сразу. Сдвиг времени мог активировать ALife-события, а история прогрузки и системное состояние различались; это не финальная полностью идентичная пара и по-прежнему не тест штатного Windows EXE. Её достаточно, чтобы **не объявлять native быстрее Silo**.

Попытка исправить именно test harness (`matched_profile_calendar_weather_v2.lua`) намеренно прервала Silo до замера: первые два его кадра заняли ~14 секунд и часы перепрыгнули целевую отметку. Следующая версия сценария дождалась `Environment::OnFrame` перед погодной паузой и завершила оба запуска (`runs/r1-final-weather-v3-01`), но *тоже не получила идентичные условия*: при старте окна Silo показывал 08:21:49, native 08:21:03; weather weight 0,05885 против 0,01421, far plane 652,77 против 649,15, wind 422,35 против 428,15. Команда понижения game factor до 0,1 в actor callback не удержала часы во время длинного первого Silo кадра. Диагностически Silo получил On-Glass 41,54 FPS, native 22,39; эту большую разницу **нельзя публиковать как matched FPS пары** из-за названных погодных и временных расхождений. Она подтверждает необходимость исправить метод сравнения и исследовать основной native frame budget, а не оптимизировать под случайно выбранную низкую Windows цифру.

Был обнаружен отдельный артефакт измерения: после CUA-доступа к окну native callbacks сохраняли примерно 24–25 FPS, но `metalperftrace` считал лишь 13–16 On-Glass FPS. Без CUA в течение всего прогона та же R1-сборка дала 24,6564 callback и 24,6592 On-Glass FPS при 419 samples; итоговая обычная сборка выше также дала совпадающие величины. Причина в цепочке UI/compositor не локализована, поэтому окно во время числовых тестов не открывается/не снимается и точный механизм не заявлен.

## Отвергнутые идеи и дальнейший критерий

Измерения отклонили local-light MSC binding reuse (нет выигрыша FPS), resource dedup (нет выигрыша), маленький static-shadow PSO reuse (разница около 1,2% с ухудшением CPU p50), сложное группирование Flora main draws (17 из 11 663 соседних source draws, 0,15%; видимый порядок может несколько отличаться), и source-parent-sphere admission: на фактически наблюдённом кадре пять отвергаемых сферой родителей не дали ни одной реально нарисованной грани или material draw. Код этих экспериментов из основного renderer возвращён к prestate; их артефакты сохранены в `scratch/native-silo-parity-20260929/`.

Следующая исследованная **гипотеза, пока без подавления в рабочих исходниках**, — Windows SSA discard/устойчивое thinning для мелкой статической геометрии. Windows применяет его к каждому visual до графа, а visible main Flora Metal пока делает только conservative clip. В отдельном observe-only бинарнике, не оставленном в основной сборке, кадр 700 записал все **5 316 фактически отправленных main Flora visual ID**. `.submitted` serial и E01 completed frame 700 совпали; каждый ID и leaf/trunk материал точно соединён с OGF_HEADER активного архива уровня SHA-256 `1800a451d0bba9af1da69fae8683b36b6e6346709c0d6b9bf14385f4a48d19f7`.
