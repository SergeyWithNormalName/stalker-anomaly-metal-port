# GAMMA через Silo и Direct Metal: время кадра

Дата: 29 сентября 2026. Машина: MacBook Pro M1 Pro, 16 GB, macOS 27.2 beta, питание от сети. «Windows» здесь означает установленный AnomalyDX11.exe под Silo/Wine-CX 26.3.0, Rosetta и GPTK/D3DMetal 4.0 beta 2 на этом же Mac.

## Что удалось проверить

В обоих случаях создан полноценный новый мир через обычную форму GAMMA New Game и её `OnStartGame()`: одиночка, Кордон / деревня новичков, обычные начальные настройки формы. Это не запуск голой карты через debug F2. Мир, NPC и игровое время работают: Device clock = 1, game time factor = 6. У порта после перехода из fake_start потребовалось продолжить только что созданный начальный autosave и снять стартовую паузу до прогрева. Для повторного запуска использован этот же начальный autosave.

Native E01/E07 instrumentation включена; её overhead против полностью выключенного режима в этом расследовании не калиброван. Поэтому это диагностические результаты, а не принятый renderer A/B.

Каждый основной замер: 60 секунд прогрева, 120 секунд записи, исключены первые 10 секунд записи с диагностическим CPU sampling. Камера неподвижна на штатной точке появления, смотрит вдоль +Z. Это измерение обычной симуляции в стартовой сцене, не маршрута игрока по всей локации. Физический размер drawable в обоих путях 1920×1200, VSync выключен. Реальная телеметрия не показывает MetalFX scaling или frame interpolation в этих окнах, несмотря на включённый параметр MetalFX у Silo.

Игры использовали собственные scratch appdata, конфигурации и сохранения; Wine — копию bottle. Установленная игра, оригинальный Wine prefix и пользовательский профиль не служили местом записи. Нативный binary SHA256 `b0bcf586c65fdb8bad8034202b3df96f0786d7fefaf4f8d9e1b411c29fc323cc` и оригинальный `runtime/macos-gamma/appdata/user.ltx` SHA256 `b292cb881b7ac66c1bc9f5ffdb9ff9efd20bd253c37a408bb086f20ec202209e` проверены после запуска и совпадают с начальными.

| CPU scene | 35.63 | 69.14 | Внутри encode |
| Dynamic prewarm | 7.64 | 10.34 | Внутри scene; подготовка динамических моделей |
| CPU skin repack | 5.11 | 6.67 | Внутри prewarm, обработка изменившихся поз |
| Skin upload | 1.11 | 1.31 | Вложенная подготовка skin buffer |
| Bounds | 0.327 | 0.455 | Вложенный проход вычисления границ |
| Local-shadow CPU | 13.67 | 31.56 | Внутри scene; не только динамические модели |
| Sun-shadow CPU | 3.95 | 3.78 | Внутри scene |
| GPU execution elapsed | 22.04 | 37.60 | Отдельная сторона конвейера, перекрывается с CPU |
| nextDrawable wait | 0.0095 | 0.0077 | Не основной источник типичного торможения |

**Строки нельзя складывать.** CPU encode, scene, prewarm и skin — вложенные таймеры; GPU работает с перекрытием по кадрам. Runtime `CPU End-to-End Walltime Interval` (~55.85 / 104.61 мс) также не является CPU busy time и не складывается с encode. GPU elapsed — длительность GPU command buffer, не измерение occupancy, bandwidth или cache pressure.

Типичный кадр порта ограничен прежде всего CPU-подготовкой/кодированием: 37 против 22 мс в первом окне, 71 против 38 мс в повторном. При этом GPU тоже существенен. Основной бюджет CPU находится в сцене и особенно локальных тенях; skinning добавляет несколько миллисекунд, но не объясняет весь разрыв. Высокий pose reuse и редкие cache misses исключают объяснение «кэш скелетов совсем не работает». Изменившиеся позы всё равно требуют CPU repack.

Отдельный diagnostic пользовательского тяжёлого сейва дал ~11.47 FPS, CPU encode 66.50 мс, prewarm 14.37 мс, skin 9.91 мс, local shadows 20.54 мс, GPU ~30.08 мс. Там календарь/погода удерживались; это полезный бюджет тяжёлой сцены, но не дополнительный normal-newgame A/B.

## Что известно про путь Silo

Достоверно измерены весь игровой цикл и показ кадров. CPU sampling старого Windows EXE разрешён по его PDB: в стэках есть обход статической сцены и render graph, установка констант, расчёт костей, движение/AI, spatial/ray queries, LuaJIT и финальное объединение кадра. D3DMetal использует собственные рабочие очереди. Это качественная атрибуция; перевести плохой unwind Rosetta sampling в миллисекунды AI/рендера нельзя.

Независимые process resource counters дают ещё один CPU результат за измерительные окна: Windows/Silo расходует примерно **41.6 CPU-ms на callback**, первый Metal — **79.3**, повторный Metal — **106.9**. Это разность накопленных CPU user+sys seconds, делённая на callbacks в том же интервале, по всем потокам процесса. Она подтверждает более высокий общий расход CPU на кадр у порта в этих сценах, но **не является последовательной длительностью кадра** и не разбивает CPU на AI/renderer/driver. Потоки перекрываются; 42 CPU-ms при 27-мс типичном цикле не противоречат друг другу. Из-за секундного timestamp Lua есть погрешность счёта порядка 1%; артефакты — `cpu-resource-summary.json` каждого основного запуска. Footprint в конце окон: ~10.8 GiB у Silo, ~6.1 / 6.8 GiB у Metal; эти разные сцены не доказывают причину отдельных пауз или paging.

Per-drawable runtime telemetry у D3DMetal не связывает основную GPU-работу с CAMetalLayer: почти все строки имеют `Command Buffer Count = 0`, `On-GPU = 0`. Эти нули **не являются временем рендеринга GPU**. Её CPU API span ~0.676 мс относится к наблюдаемому пути present, а не всему CPU-рендеру Windows. Сравнивать его с native encode 37–71 мс ошибочно.

Отдельный Instruments Metal System Trace успешно снят в повторном полном новом мире Silo (`w_cloudy3_dark`) после прогрева, вне основного FPS-замера. Trace: 02:28:36.307–02:28:53.605 UTC; target PID 6797. Экспорт `metal-gpu-intervals` валиден: 171 065 строк всех процессов, из них 91 166 Active GPU intervals этого Wine-процесса, 3 052 command buffers, 514 последовательных trace frame IDs. Вложенные и перекрывающиеся интервалы объединены, а не сложены.

| Silo GPU, union Active intervals по trace frame | p50 | p95 | Покрытие |
|---|---:|---:|---|
| Все каналы GPU вместе | 27.11 мс | 29.89 мс | 514 trace frames |

Категории перекрываются и их медианы не складываются. Это **GPU active union**, тогда как native 22–38 мс выше — command-buffer elapsed span; точную разницу этих метрик нельзя объявлять backend speedup. Первая/последняя trace frames могут быть неполными; после их исключения p50 остаётся 27.11 мс. Группировка согласуется с реальным cadence: за соответствующее активное окно GPU зарегистрированы 514 trace frames и 516 Lua callbacks, медианы стартового интервала GPU / игрового цикла 30.50 / 31 мс. Секундный Lua epoch не позволяет сопоставить каждый отдельный ID точно; числа подтверждают соответствие масштаба, не математически точную идентичность frame IDs.

Объединение всех Active GPU intervals Wine занимает 13.691 секунды из активного окна 16.665 секунды (~82.2% времени этого окна). Это timeline activity fraction, **не аппаратный shader occupancy**. По отдельным каналам union за окно: Fragment 11.814 s, Vertex 1.264 s, Compute 1.093 s; каналы перекрываются, их нельзя складывать. Таким образом, большая часть наблюдаемой GPU-работы Silo приходится на fragment/render, с небольшими transfer/compute затратами. Семантические названия R4 shadow/G-buffer/lighting passes в экспортированных D3DMetal encoders отсутствуют, поэтому отдельные GPU-миллисекунды каждого такого pass здесь не установлены.

Time Profiler export этой трассы оказался непригодным (один sample и обрезанный XML); это не CPU-stage budget. Точные CPU-миллисекунды Windows AI, graph build, skinning и D3DMetal workers остаются открыты. Общий CPU resource budget и качественный PDB audit выше пригодны; разложение Windows CPU по стадиям не следует выдумывать.

## Подтверждённые различия реализации

1. **Отсечение скрытой статической геометрии.** Windows R4 загружает sectors/portals и HOM, применяет их к статическому графу. Metal level loader выходит раньше загрузки sectors; manual static-level draw обходит отдельный массив с консервативным frustum test. В этой ветке нет эквивалента Windows portal/HOM rejection. Общий Calculate всё ещё вызывает `GMBase.traverse`, однако нормальный Metal level load не загружает необходимый D3D sector/HOM graph. Часть общих SSA/LOD решений остаётся. Это основание ожидать лишнюю CPU/GPU-работу в закрытых сценах, но её размер ещё не измерен в matched Cordon.
2. **Скрытые локальные источники света.** Windows R4 использует light visibility / occlusion queries и HOM/sector gates. Metal не создаёт D3D query, а обычная light snapshot ветка ограничивается frustum/range/fog/LOD. Поэтому закрытые стенами лампы могут приносить лишние shadow views. У Metal уже есть static caster spatial index, exact frustum tests, merged-index cache и atlas batching: утверждение «никакого shadow culling/cache нет» неверно.
3. **Обработка скелетов.** Windows поддерживает hardware vertex-shader skinning для 1–4 весов с software fallback. Metal CPU-перепаковывает вершины изменившихся поз и загружает готовый buffer, переиспользуя его между G-buffer и тенями. Это реальная дополнительная CPU-работа; она не повторяется полностью для каждой теневой грани.
4. **CPU кодирование сцены.** Metal `scene.Render()` выполняется внутри основного `End()` перед commit. Асинхронный GPU completion не делает CPU encoding параллельным. При этом legacy `CRender::Render()` сразу возвращает в Metal: полного двойного D3D+Metal рендера нет.

Настройка `r__hom_dynamic off` в сравниваемых конфигурациях выключает динамический HOM. Её нельзя приводить как активное преимущество Windows в этих замерах. Это не отменяет различия статического HOM/порталов и light visibility.

Исходные указатели: `src/Layers/xrRenderPC_R4/r4_loader.cpp:35–59,128–141`; `src/Layers/xrRender/r__dsgraph_build.cpp:1297–1367`; `src/Layers/xrRenderMetal/MetalR4EngineScene.mm:1236–1264`; `src/Layers/xrRender/light_vis.cpp:12–116`; `src/Layers/xrRender/r__dsgraph_render.cpp:966–1023`; `src/Layers/xrRender/SkeletonX.cpp:266–413`; `src/Layers/xrRenderMetal/MetalR4DynamicWorldAdapter.cpp:2370–2489`; `src/Layers/xrRenderMetal/MetalRenderDeviceRender.mm:1625–1702`. Подробный source audit сохранён в scratch `windows-path.md` и `metal-path.md`.

## Что исправлять и сколько можно получить

**Основной приоритет — уменьшать работу сцены и локальных теней.** Сначала наблюдаемая проверка скрытых lights/casters при одинаковом состоянии мира, затем корректное HOM/portal/light rejection с доказательством отсутствия пропавших теней. Бюджет local-shadow CPU 13.7–31.6 мс достаточен, чтобы направление было важным; он не означает, что столько можно целиком убрать. Предыдущий whole-light HOM diagnostic на другой fixture оценивал ~2.4 мс потенциальной чистой CPU-экономии, а не измеренный прирост Cordon FPS.

**GPU skinning — следующий существенный кандидат.** Его gross CPU budget 5.1–6.7 мс в свежем мире, ~9.9 мс в тяжёлом сейве. Перенос работы на GPU не бесплатен. Простое vertex skinning в каждом shadow pass повторит работу на миллионах вершин; более подходящий для нынешнего cache contract вариант — compute skin once с переиспользованием GPU buffer. Нужна проверка 1–4 весов, normals/tangents, motion, bounds и владения buffers между кадрами. Измеренного net gain пока нет.

**Малые CPU изменения:** hoist immutable pose hash из geometry loop, повторно использовать scratch vertex vector. Их собственная доля не измерена, поэтому весь prewarm нельзя выдавать за ожидаемую экономию. Замена второго vertex bounds pass на консервативные transformed AABB corners ограничена бюджетом ~0.33–0.46 мс и сама по себе проблему не решит.

Повторно запускать отклонённый parallel static-shadow packet encoder оснований нет: прежний A/B дал 1.246 мс direct против 1.757 / 2.654 мс с 2 / 4 workers. Это не запрещает отдельно проверять другие задачи подготовки.

Арифметические ориентиры ниже — **не прогноз оптимизации**. Предполагается удаление времени прямо из последовательного критического пути без роста другой части:

| Типичный цикл | Сейчас, reciprocal p50 | Минус 5 мс | Минус 10 мс |
|---|---:|---:|---:|
| 43.115 мс | 23.19 FPS | 26.24 FPS (+13%) | 30.20 FPS (+30%) |
| 75.596 мс | 13.23 FPS | 14.17 FPS (+7%) | 15.24 FPS (+15%) |

Для 20 FPS типичный тяжёлый 75.6-мс кадр нужно сократить минимум на ~25.6 мс. Для 30 FPS — на ~42.3 мс, плюс GPU ~37.6 мс должен стать меньше 33.3 мс. Для 60 FPS нужны оба бюджета ниже 16.7 мс: это большая переработка сцены/теней и GPU-работы, а не одна небольшая skin/bounds правка. Даже достижение медианы 20 не доказывает минимум 20 на всей локации; длинные паузы требуют отдельного исследования.

## Почему предыдущие бенчмарки обещали больше

E08 S4 был фиксированной fixture с остановленным Device clock; S2 использовал другие условия карты/камеры/объектов. Они проверяли конкретные renderer changes, но не минимальный FPS полной GAMMA-симуляции. Старый 1920×1080 Silo профиль также обрабатывал на 11.1% меньше пикселей, чем 1920×1200 порт; это исправлено в нынешних запусках. HUD в текущем engine использует сглаженный/clamped frame delta с пределом 0.1 s, поэтому показанные 10 FPS могут скрывать более длинные реальные кадры.
