# E06 — Windows luminance source contract (bounded audit)

Read-only source review. No source, cook, build, game, or capture changes made.

## Confirmed missing producer

Windows `phase_bloom()` first builds `rt_Bloom_1` from `r2_RT_generic1` using `s_bloom->E[0]`, then calls `phase_luminance()`; with `o.ssfx_bloom`, it returns only after luminance (`src/Layers/xrRenderPC_R4/r4_rendertarget_phase_bloom.cpp:73-143,146-150`). The active producer is `bloom_build.ps`, bound to `r2_RT_generic1` and `smp_rtlinear` (`src/Layers/xrRenderPC_R4/blender_bloom_build.cpp:18-24`). Luminance element 0 reads `r2_RT_bloom1`, not generic1 (`src/Layers/xrRenderPC_R4/blender_luminance.cpp:18-23`).

`rt_Bloom_1` is 256×256 `D3DFMT_A8R8G8B8`; `BLOOM_size_X/Y` are both 256 (`r4_rendertarget.cpp:867-882`, `r2_types.h:137-138`). For the E06 SDR path, source `generic1` is full-resolution A8R8G8B8 (`r4_rendertarget.cpp:529-539`). Current Metal instead feeds full-resolution `scene.lightingTargets[1]` directly to the 64×64 luminance pass (`src/Layers/xrRenderMetal/MetalBootstrap.mm:3206-3210`); Metal lighting targets are full-resolution RGBA8 (`:2869-2885`). No 256×256 bloom-preluminance target/pass is currently allocated or drawn. This is a confirmed producer gap in the active luminance source chain.

## Exact producer contract

- **Shader and input:** `stub_notransform_build.vs` + `bloom_build.ps`; input `s_image = r2_RT_generic1`, sampler `smp_rtlinear` (`blender_bloom_build.cpp:18-24`). The VS takes a Float4 position and four Float2 UV sets (`stub_notransform_build.vs:5-20`). The PS takes `b_params` and samples all four UVs with `smp_rtlinear`, averages the four RGB values, and writes alpha `1-b_params.x` (`build/metal-shader-sources/r3/bloom_build.ps:3-41`).
- **Target and order:** `rt_Bloom_1`, 256×256 A8R8G8B8, no depth; its full-quad producer runs before luminance's 256→64 pass. Existing Windows code does not clear before the draw (`phase_bloom.cpp:73-83`), whose quad covers the target (`:106-143`).
- **Vertex UV construction:** with source dimensions `W×H`, target `tw=th=256`, `aspectW=(W/2)/256`, `aspectH=(H/2)/256`; `one=(1/W,1/H)*aspect`, `half=(0.5/W,0.5/H)`, `a_i` are the four half/one offsets and `b_i=a_i+(1,1)` (`phase_bloom.cpp:85-104`). Vertex positions are `(EPS,256+EPS)`, `(EPS,EPS)`, `(256+EPS,256+EPS)`, `(256+EPS,EPS)`; each vertex receives the appropriate `a_i`/`b_i` component pairing (`:106-132`). At 1920×1080, `one=(0.001953125,0.001953125)`, `half=(0.0002604167,0.0004629630)`; `a0=half`, `a1=(half.x+one.x,half.y)`, `a2=(half.x,half.y+one.y)`, `a3=half+one`, and every `b_i=a_i+(1,1)`. Fragment `screen_res` is the full device `W,H,1/W,1/H`: HLSL uses `screen_res.x/screen_res.y` to adjust each UV around `UVavg` (`bloom_build.ps:10-23`). Metal currently uses target-sized VS normalization globals for its 256-quad, as required by its screen-quad conversion; do not infer a Windows parity mismatch from the separate pixel-stage `cl_screen_res` binder.
- **Constants and resources:** Windows sets `b_params=(threshold,threshold,threshold,f_bloom_factor)`; threshold is `ps_r2_ls_bloom_threshold`, while the factor is updated as `0.9*old + 0.1*ps_r2_ls_bloom_speed*deltaTime` (`phase_bloom.cpp:134-142`). In this active PS only `.x` is read (`bloom_build.ps:38-41`); preserve the authored full vector, but `.yzw` do not affect this shader output. `bloom_build.ps` DXIL reflection gives `$Globals` CB0 size 176 with `b_params` at byte 160, `static_globals` CB1 size 528 with `screen_res` at byte 416, `s_image` t0, `smp_rtlinear` s0; MSC TLAB is SRV@0, CBV@24, CBV@48, Sampler@72 (from `build/metal-runtime-shaders/luminance-e06/bloom_build.ps.dxil.txt` and `.reflection.json`). The VS uses one 528-byte static-global CBV at TLAB offset 0.

Sampler fidelity matters: Windows `smp_rtlinear` is clamp-address, linear min/mag, point mip (`src/Layers/xrRenderPC_R4/CSCompiler.cpp:39-46`). Current Metal `lightingLinearSampler` is repeat-address and linear mip (`MetalBootstrap.mm:1905-1913`), so it is not a substitute for the new producer's RT-linear sampler.

## Minimal central integration proposal

Add an owned 256×256 RGBA8 renderable/readable `luminanceBloom256` target, a `bloom_build.ps` PSO using the already cooked `stub_notransform_build.vs`, its four-UV quad, a 176-byte globals slice with `b_params`, a 528-byte fragment static-global buffer for the device/source dimensions, and a clamp/linear/point-mip sampler. Draw it from `scene.lightingTargets[1]` before the current 64×64 pass. Redirect that pass to `luminanceBloom256` and regenerate its existing build UVs for 256×256; retain full device `screen_res` for the fragment constants in both `bloom_build` and `bloom_luminance_1`. Capture `ps_r2_ls_bloom_threshold` from the authoritative live R4 value; `R4EnvironmentSnapshot` currently has tonemap and SSFX bloom controls but no `r2_ls_bloom_threshold` field (`IR4Backend.h:203-215`, `dxEnvironmentRender.cpp:400-405`). Leave the 64→8→1 chain and adaptation target alone.

The existing `drawLuminancePass` binds one fragment CBV only (`MetalBootstrap.mm:3148-3181`), while `bloom_build.ps` requires two; use a small dedicated binding helper or extend that helper to express both CBVs. Keep this producer distinct from `MetalR4BloomAdapter`: it creates the luminance input texture before `bloom_luminance_1`, not the SSFX bloom pyramid/output.

`script/compile_r4_luminance_msc.sh` currently cooks the two build/filter VSs and three luminance PSs, but not `bloom_build.ps` (`:26-33,97-103`). A receipted E06 effects bundle already contains `bloom_build.ps` artifacts and hashes (`build/metal-runtime-shaders/luminance-e06/effects-msc-receipt.json:703-706`), but production luminance admission validates only five artifacts and requires its separate `luminance-msc-receipt.txt` (`MetalBootstrap.mm:1028-1088`). Minimal release-grade integration should include the new PS in the luminance cook/admission receipt and validate its 96-byte fragment TLAB/constant-buffer layout before PSO creation.

This finding covers only the missing luminance producer; it does not claim SDR visual parity or alter central graph ordering.

## Review of the current central integration

Read-only review of the follow-up implementation found the producer’s UV lane math, vertex order, `EPS=1e-5`, target-normalized VS globals, threshold frame owner, target format, and clamp/linear/point-mip sampler consistent with the Metal screen-quad contract. The existing 64×64 vertex quad remains at 0..64 with its original `.5/source` UV offsets; its `stub_notransform_build.vs` still adds the authored half-pixel shift. I checked the pixel-stage `screen_res` against the original binder: `cl_screen_res` always reads `RDEVICE.dwWidth/dwHeight` (`src/Layers/xrRender/Blender_Recorder_StandartBinding.cpp:610-617`; `RDEVICE` is `Device` at `src/xrEngine/device.h:520-526`), and `u_setrt(rt_LUM_64)` does not change those drawable dimensions. Therefore keeping the full drawable `screen_res` when `bloom_luminance_1` samples square `rt_Bloom1` is intentional: its HLSL uses the display aspect to scale the sample pattern (`build/metal-shader-sources/r3/bloom_luminance_1.ps:21-33`). The current shared `luminanceBuildFragmentGlobals` full drawable dimensions match this Windows pixel-stage binder; no corrective split to 256×256 is indicated. The new producer's `.00001` positions plus shader's `.5` pixel shift also match the authored 256-quad path. I did not infer a Windows/Metal VS screen-res discrepancy from the pixel-stage binder. No concrete defect was found in the reviewed additions. Build/runtime verification remains with the integrator.
