# E02 frame data ownership contract

State: implemented for the inspected production call sites; lifecycle retry/resize test remains open. This contract applies to Direct Metal R4 draw, pass, and frame uploads.

1. `BeginFrame` acquires a backend context by its semaphore. Only the acquired `ActiveFrameContextIndex` owns its transient upload blocks. The backend resets that context's upload cursor after its prior command buffer completes. An engine frame number or submission serial never selects an upload slot.
2. `UploadFrameData` copies input bytes to a fresh aligned range and returns `{buffer, offset, size}`. Callers bind the returned slice for every draw or pass whose bytes differ. They never update a previously bound slice. The input may go out of scope after the call. The entire native buffer and the slice remain alive through GPU completion.
3. Constant buffers entering MSC bindings through legacy persistent Shared buffers are snapshotted once per binding into the same frame arena. Callers that already pass a frame-upload slice skip this copy. Dynamic vertex and instance call sites should use explicit slices. For remaining persistent Shared vertex/index buffers, backend bindings retain the exact native version; a later `UpdateBuffer` copies on write before changing bytes. This fallback preserves old draws without copying static geometry on every bind.
4. Alignment is at least 256 bytes for constant buffers and 16 bytes for vertices. Each allocation checks addition/rounding overflow and native buffer bounds. Spill blocks belong to their acquired context, are reused only after completion, and are retained at the high-water mark. The upload arena, MSC TLAB, and Shared vertex/index copy-on-write each have a 128 MiB per-context cap. Persistent meshes and textures stay outside this arena.
5. Failed acquisition, encode, or submit does not advance the submission serial or temporal history. A retry may reset a slot that has no active GPU work. Render targets and history textures remain ordered on the serial command queue unless a separate hazard is proven.

Verification: an old-path GPU probe must observe AO/IL and blur bytes overwritten before submit. The corrected path must preserve distinct per-pass values, distinct draw transform/color values, and patterns across 3–6 queued frames. Forced slot reuse, retry/failure, alignment, overflow, validation, memory high-water, S1 motion, and before/after FPS are E02 exit checks. Passing build or CPU-only checks does not close those gates.

## Evidence on 2026-09-23

- `XRay.Metal.FrameUploadGpuProbe --old-path` exits 1 with `old Shared buffer overwrite reproduced before submit`. The six readbacks represent AO, IL, and four blur values from one reused Shared address.
- `XRay.Metal.FrameUploadGpuProbe --self-test` passes under `MTL_DEBUG_LAYER=1` and `MTL_SHADER_VALIDATION=1`. It checks six queued frames with no immediate wait, completed-slot reuse, vertex/index copy-on-write, slice alignment and rejected overflow, plus two real draws with distinct transform/color slices and pixel readback.
- The S1 Direct Metal validation fixture exits 0 with no Metal assertion or backend error; its TLAB shutdown report is three blocks totaling 48 MiB. The normal S1 fixture exits 0, reports `status: OK`, and contains a 15.09 s moving-camera recording. Evidence paths are in `STATUS.md`.
- AO/IL and water advance their CPU history state and release their first-use upload bytes only after successful `SubmitFrame`. On a later render after an encode failure, pending state is discarded; a known asynchronous command-buffer error fails the next `BeginFrame` closed.
- An explicit automated drawable retry/resize/failed-encode lifecycle run against the complete backend remains **OPEN**. The standalone backend-link probe could not link without the game executable's engine globals; it was removed rather than leaving a failing registered test. Code inspection and S1 do not substitute for this test.
