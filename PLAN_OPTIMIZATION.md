# Ограниченная проверка оставшихся способов ускорения Direct Metal

Дата: 2026-09-28. Статус: **ОГРАНИЧЕННЫЙ РАУНД ЗАВЕРШЁН; нового принятого FPS gain нет.** Текущее поручение пользователя разрешает код, сборки и ограниченные бенчмарки; экономим батарею. Результаты: [OPTIMIZATION_PROBES.md](docs/direct-metal-release/OPTIMIZATION_PROBES.md).

## Решение

Продолжить ограниченное исследование CPU submission: parallel render encoding и сокращение повторной подготовки MSC bindings. CPU-encoded ICB оставить условным следующим кандидатом. Не начинать бессрочную переделку рендера ради обещанных 60 FPS.

Предыдущий вывод «дальнейшую оптимизацию остановить» был слишком широким. E08 убедительно проверил несколько обычных оптимизаций, но не проверял `MTLParallelRenderCommandEncoder`, Residency Sets, устойчивые к смене кадров таблицы MSC или повторное исполнение CPU-encoded ICB. Отрицательный результат resource dedup не исключает Residency Sets: это разные способы организации работы.

Значимость этих гипотез подтверждается профилем CPU; размер возможного ускорения неизвестен. Достижимость стабильных нативных 1080p60 остаётся открытой. При составлении этого плана игра, probes, сборки и новые замеры не запускались. 2026-09-28 пользователь поручил выполнить план с ограниченным числом бенчмарков; прежний запрет на выполнение больше не является границей этого раунда.

## Исходные данные и границы вывода

Последняя измеренная production-сборка E08: `d9ccd643ba6d83b27e83a2e50141a96c7c0cb40323fa74b8f1b1f9a2d7ea2e55`. Это идентификатор исторического эксперимента, не утверждение о текущем бинарнике после других правок.

- Финальная матрица native 1920×1080: медианы S0/S2/S4/S5/S6/S7 — 24/30/24/40/30/40 FPS.
- S4: CPU encode p50/p95 = 39,463/41,338 мс; GPU frame p50/p95 = 23,708/24,994 мс. Полная запись презентации: средний FPS 23,08; 1% low 14,61; displayed p99 58,33 мс.
- Финальный диагностический профиль тяжёлой камеры, 11 кадров: local atlas CPU 15,473 мс, G-buffer CPU 12,429 мс; вложенная общая категория MSC binding 9,947 мс, indexed draw 3,455 мс.
- Последние категории вложены в проходы; их нельзя прибавлять к стоимости проходов. Медианы разных выборок не образуют точный бюджет одного кадра. GPU stage spans могут перекрываться.
- Наивное деление всего CPU encode на число потоков недопустимо. Подготовка данных, синхронизация, последовательные проходы и конкуренция с игровыми потоками останутся.
- GPU frame span не является доказательством предела железа или чистого времени ALU. После ускорения CPU нужно заново проверить GPU и критический путь; текущие 23–25 мс не позволяют обещать 60 FPS.
- Матрица содержит один прогон на сценарий. У пяти сценариев неполная запись презентации. Полная AI-нагрузка, холодное перемещение и длительная работа не приняты.

## Общие правила будущих экспериментов

1. Сохранить существующий WIP и получить точный manifest исходников, бинарника, shaders, save/config, сценария и физических размеров рендера. Не сравнивать новую сборку с историческим E08 как изолированное A/B. Контроль и кандидат должны переключаться в одной новой сборке.
2. Ограничить правки Metal backend и одной выбранной семьёй рисования. Сохранить прежний serial путь как oracle/fallback. Не менять AI, физику, скрипты, позы, качество, свет, список геометрии или DXVK/MoltenVK fallback.
3. Сначала проверить корректность на реальных converted shaders и положительном покрытии; затем короткий representative probe. Синтетический выигрыш разрешает проверить игру, но не доказывает ускорение игры.
4. Будущие игровые сравнения: сначала S4 и контрольная S2, одинаковая временная линия, AC/термальные условия, 60 с прогрева + 150 с окна с исключением первых 30 с сценария. Чередовать A/B/B/A. Не смешивать timing с validation, capture, hardware counters и подробным логированием.
5. Считать wall time критического CPU-пути, весь кадр, GPU duration, фактически показанные интервалы p50/p95/p99 и 1% low; отдельно затраты workers и ожидание join. Сумма CPU-времени workers не равна задержке кадра.
6. Предлагаемый экономический порог для расширения прототипа: воспроизводимое сокращение CPU encode p95 на S4 хотя бы на 3 мс и 10%, превышающее разброс контроля. Это критерий решения, не прогноз и не native60 gate. Для production нужна полезная перемена целого кадра/показанного FPS либо доказанный необходимый запас после смены bottleneck; не принимать лишь ускорение внутреннего таймера.
7. Память должна иметь явный предел и освобождаться после GPU completion; отсутствуют существенные регрессии GPU, кадровых хвостов, input latency и контрольной S2. Ошибочные/упавшие прогоны исключать, сохраняя их как свидетельство дефектов.
8. На каждый основной кандидат — первоначальный прототип и не более одной доработки по конкретной найденной причине. При неразличимом результате допустим один повтор блока; дальнейшее расширение объёма означает STOP и новый пересмотр целесообразности.

## P0 — установить, какую работу можно убрать или распараллелить

**Цель:** ограничить стоимость последующих probes; не начинать общий рефакторинг backend.

- Для S4 отделить внутри MSC binding: построение списков ресурсов в адаптере, проверки/приведения типов, копии констант, TLAB allocation/fill, `useResource`, удержание владельцев и сам Metal binding. Существующие 9,947 мс — только агрегат backend; часть подготовки находится снаружи.
- Выделить CPU preparation и собственно encoding в одной выбранной части G-buffer или local-shadow pass. Оценить, какая часть может работать с неизменяемыми данными.
- Составить карту общего изменяемого состояния: encoder/PSO state, frame upload arena, TLAB offsets, retainedResources, indirectReads, статистика, scratch адаптера, обновления uniform buffers.
- Проверить стоимость инструментирования отдельным on/off сравнением; если она велика или неразличима на фоне шума, данные служат лишь диагнозом, решение принимается по обычному A/B без подробных таймеров.

**Блокеры:** `FrameContext` сейчас один для активного кадра; его контейнеры и allocators не рассчитаны на конкурентную запись. MSC binding копирует меняющиеся shared constants в неизменяемые slices. Нельзя удалить эти копии или защитные проверки только ради красивого результата.

**Выход:** таблица устранимых/параллельных затрат, выбранный узкий участок, список владельцев данных. Кандидат допускается дальше, если есть правдоподобный резерв относительно порога в пункте 6 общих правил; если данных недостаточно, он остаётся непроверенным.

## P1 — Residency Sets и повторное использование bindings: два отдельных A/B

По потенциальному масштабу parallel encoding интереснее, но этот этап может оказаться дешевле. После P0 выбрать порядок по ожидаемой цене проверки. Провал P1 не закрывает P2.

### P1a. Residency Sets для неизменяемых ресурсов

**Гипотеза:** повторные declarations для одних и тех же static VB/IB/textures требуют заметного CPU-времени, которое можно убрать постоянным набором.

- Проверить availability/capabilities: API есть в обычном `MTLCommandQueue` с macOS 15; миграция всего backend на `MTL4CommandQueue` не нужна. Сохранить fallback.
- Начать с ограниченного набора неизменяемых ресурсов выбранного прохода. Добавлять после завершённой загрузки; пакетировать изменения по созданию/уничтожению, не пересобирать set на каждый draw.
- Временно изменяемые render targets, uploads и ресурсы со связями write→read оставить на прежнем корректном пути. Residency не заменяет hazard tracking. До удаления `useResource` доказать синхронизацию для каждого затронутого ресурса.
- Сравнить с тем же путём без sets. Удержание lifetime и состав рисования одинаковы; изменение лимита памяти не должно скрывать стоимость.

**Блокеры:** удаления при in-flight frames, загрузка/смена уровня, recovery после discard; потеря hazard tracking; слишком широкий постоянно resident набор на машине с 16 ГБ общей памяти.

**STOP:** declaration path слишком мал; экономия исчезает в управлении sets; нужны глобальная перестройка синхронизации или неограниченная residency. Не объявлять отрицательный результат общей дедупликации из E08 проверкой P1a.

### P1b. Повторное использование таблиц MSC

**Гипотеза:** у статических материалов повторно создаются одни и те же descriptors и списки привязок. Argument buffers уже применяются; задача — сократить их пересоздание.

- Разделить неизменяемые material descriptors и меняющиеся frame/view/object данные без изменения shader ABI на первом прототипе.
- Проверить один материал/семейство: допустимы подготовленные шаблоны и безопасные версии на frame slot; фиксировать реальную экономию allocation/fill/copy/bind.
- Нельзя кешировать TLAB только по имени материала: GPU address, offset и generation констант меняются, световые матрицы отличаются между tiles, прежние frames ещё выполняются.
- Один и тот же mesh в разных light views, движение камеры, несколько frames in flight и submit retry должны получать собственные корректные данные.

**Блокеры:** copy-on-write меняет backing allocation; immutable frame slices и их offsets; нестатические текстуры; рост cache. Если весь выигрыш требует нового bindless ABI во всех shaders, этот этап остановить.

## P2 — parallel encoding одного render pass

**Гипотеза:** существенная часть измеренных CPU-затрат прохода может выполняться одновременно на 2–4 CPU workers. API сам не распараллеливает существующий цикл.

1. Выбрать один участок с уже подготовленными immutable draw packets: предпочтительно однородную часть G-buffer либо один тяжёлый atlas batch. Не распараллеливать AI, захват движковой сцены или обновление костей.
2. Сделать serial вариант тех же packets, чтобы видеть стоимость подготовки отдельно. Сравнивать также с исходным прямым путём: ускорение относительно искусственно замедленного serial packet builder не считается.
3. Сопоставить прямой encoder, parallel parent с одним child, затем 2 и 4 children. Это отделяет цену новой организации от выгоды потоков. Число workers ограничить; не запускать задачу на каждый draw.
4. Дать каждому worker отдельное encoder-local state и независимые или заранее выделенные непересекающиеся slices. Владельцев ресурсов и статистику свести после join. Глобальный mutex вокруг прежнего `BindMscResources` не считать решением.
5. Child encoders создавать в порядке исходных непрерывных диапазонов draws. В каждом задать весь необходимый state, включая viewport/scissor/cull/depth/stencil. Сохранить порядок команд, attachments и load/store semantics.
6. Atlas batches с повторным использованием общей текстуры и потреблением результата оставить последовательными. Не кодировать зависимые passes одновременно через один изменяемый adapter scratch.
7. Сначала проверить реальные outputs против serial oracle, потом representative timing и только после успеха — обычный S4/S2 A/B. Считать подготовку + dispatch + максимальное время worker + join, а также влияние на остальные игровые потоки.

**Блокеры:** единый mutable FrameContext; shared uniform updates между views; owner/retry contracts; нехватка независимой работы; дисбаланс batches; конкуренция с AI/physics; возможный GPU overhead границ child encoders.

**STOP:** разделение требует протащить многопоточность через значительную часть движка; подготовка остаётся доминирующим serial этапом; 2/4 workers не дают полезной экономии целого кадра; корректность требует сериализовать почти всю работу.

**Расширение:** только после прохода порога переносить подход на вторую семью draws. Не обещать 2×/4× ускорение кадра по числу CPU threads.

## P3 — CPU-encoded ICB, условный резерв

Начинать только если P0 показывает крупную стоимость действительно повторяемых команд, а опыт P1/P2 даёт локальный контракт стабильных данных. Успех parallel encoding сам по себе не требует внедрять ICB.

- Один однородный opaque static batch, прежние converted shaders и порядок draws. Сначала проверить поддержку PSO/ICB и эквивалентность MSC draw ABI, включая index type, baseVertex, offsets и draw parameters.
- Текущий runtime helper пишет draw parameters/index-type word через `setVertexBytes`; его нельзя механически вызвать на `MTLIndirectRenderCommand`. Нужен проверенный эквивалент хранения и привязки данных.
- Повторно использовать commands, но обновлять данные камеры/света безопасно по frame slot. Статическая геометрия не означает неизменность view, visibility и списка shadow casters.
- Учитывать rebuild/update/select/execute/residency целиком. Проверить, не съедают ли экономию меняющиеся списки и границы состояний, которые ICB не может выразить на M1.
- Сравнивать с лучшим принятым прямым путём. Уже принятый static-shadow merge не выключать ради искусственно дорогого контроля.

**STOP:** ICB приходится почти полностью переписывать каждый кадр; требуются broad shader ABI/visibility rewrite; растёт GPU duration; экономия меньше затрат сопровождения. Не переходить автоматически к GPU-driven renderer.

## Что сейчас не включаем

| Идея | Решение |
|---|---|
| Tile shaders / imageblocks | Отложить. Есть большой риск изменения организации deferred passes и промежуточных данных; bandwidth bottleneck не установлен. Не начинать ради решения CPU encoding. |
| MetalFX upscaling | Отдельный пользовательский режим после повторной оценки CPU/GPU. Spatial probe уже есть; не повторять API research. Не обещать 60 при CPU около 40 мс. Temporal требует корректных motion/depth/history. Более низкое внутреннее разрешение не закрывает native1080p60. |
| Frame interpolation | Не включать в эту цель: частота сгенерированных кадров и скорость реальной симуляции/отрисовки должны оцениваться раздельно. |
| BinaryArchive / prewarm | Вернуться при доказанных compilation/first-use hitches. Не приписывать им исправление текущего steady-state encoding. |
| Heaps | Могут влиять и на allocation/residency, не только загрузку. Однако перевод ресурсов в heaps без соответствующей измеренной затраты сейчас не оправдан. |
| Flora instancing | Сохранить как непроверенный на S4 кандидат с блокером загрузки. Отсутствие принятого S4 результата не доказывает нулевой эффект. |

## Итоговый выбор после probes

- Если P1/P2 не дают материального эффекта в ограниченном объёме — остановить этот раунд. Не заполнять очередь ICB/tile/MetalFX только ради продолжения работы.
- Если есть существенный выигрыш — сохранить узкое изменение, проверить всю матрицу и заново определить bottleneck. Улучшение с 24 до условных 30–40 FPS может быть полезным, но это не доказательство пути к стабильным 60.
- Если CPU перестал ограничивать, выделить отдельную GPU-гипотезу только по новому профилю. Ускорения разных вариантов нельзя складывать: они могут устранять одну и ту же работу.
- Native60 признаётся только по прежнему release gate: по три принятых прогона всех целевых сцен, полные presentation records, средний FPS ≥60, displayed p99 ≤16,67 мс и 1% low ≥60, с учётом точной частоты дисплея. Затем capped pacing и отдельные cold/full-AI/длительные проверки. Никакой probe этот gate не заменяет.
- Production acceptance включает смену уровня, discard/retry, несколько frames in flight, сохранение качества и bounded memory. Windows parity остаётся отдельным незакрытым вопросом.

## Проверенные точки кода и API

- [MetalR4Backend.mm](src/Layers/xrRenderMetal/MetalR4Backend.mm): `BindMscResources`, `FrameContext`, `declareIndirectRead`, `retainFrameResource`, `UploadFrameData`, `UpdateBuffer`, `DrawIndexed`.
- [MetalBootstrap.mm](src/Layers/xrRenderMetal/MetalBootstrap.mm): `drawLevelScene`, подготовка per-draw stage bindings.
- [MTLParallelRenderCommandEncoder](https://developer.apple.com/documentation/metal/mtlparallelrendercommandencoder): parallel CPU encoding, порядок child encoders, ответственность приложения за синхронизацию.
- [MTLResidencySet](https://developer.apple.com/documentation/metal/mtlresidencyset): меньшие накладные расходы declarations, отсутствие hazard tracking.
- [Residency sets](https://developer.apple.com/documentation/metal/simplifying-gpu-resource-management-with-residency-sets): присоединение к command queue/command buffer.
- [Argument buffers](https://developer.apple.com/documentation/metal/improving-cpu-performance-by-using-argument-buffers): повторное использование неизменяемых resource bindings.
- [CPU-encoded ICB](https://developer.apple.com/documentation/metal/encoding-indirect-command-buffers-on-the-cpu): повторное использование команд, ограничения наследуемого состояния.
- Availability дополнительно проверена по локальному SDK `MTLCommandQueue.h`; MSC draw ABI — по используемому `metal_irconverter_runtime.h`. Наличие API не является замером его эффективности в игре.
