# Windows/native save-load failure audit

Both attempted Silo “control save” runs failed before reaching the measured phase, but neither attempted save was actually loaded. In `v9r1-vs-silo-01`, the command line includes `-load "rescue-cordon-control"` at `silo/runtime/appdata/logs/xray_crossover.log:124`; Windows startup immediately reports `ALife simulator has not been started yet` at line 707. It then logs `Creating new game...` at line 6039, writes `Player - autosave.scop` at line 7430, and later reports loading that autosave at line 13163. `windows-control-01` shows the same sequence for `parity-windows-control`: early `-load` at line 124, ALife-not-started at 707, new game at 6039, and only `player - autosave.scop` loaded at 13265. So these crashes say nothing about compatibility of either named control save.

The crash itself has `FileDownload`, empty `Description` path, and an empty `Arguments` section. Its PDB stack ends `CModelPool::Create -> CLevel::g_sv_Spawn -> CLevel::cl_Process_Spawn`; the failing entity/model name is not present. A specific saved lamp cannot be identified. The same empty-model query was recorded in earlier native V3 startup evidence, whose stack named `CHangingLamp::net_Spawn`. The current source now returns `false` for null/empty names in `CModelPool::Exists` (`src/Layers/xrRender/ModelPool.cpp:517-529`) before filesystem prefetch. The Windows executable in the tested runtime is ModdedExes dated May 15, 2026, so absence of that later guard is a plausible explanation for the blank-name failure, but the current logs do not prove that exact caller or prove which name reached `Create`.

The Windows source runtime and native canonical runtime have 4,471 regular files each under `gamedata/configs` and `gamedata/scripts`. Relative file paths and SHA-256 values match except `gamedata/configs/axr_options.ltx`. Its only differences are `session_id`, `session_start`, and `[modded_exes] version` (`20260515` Windows vs `20260929` native); none identifies a model or lamp. `gamedata/scripts/axr_main.script` is byte-identical. This makes an ordinary active config/script mismatch a weak explanation, while it does not establish identity of every binary asset or the Windows EXE’s behavior.

There is a Windows-authored save pair in the existing isolated comparison runtime: `scratch/windows-metal-gap-20260929/newgame-silo/runtime/appdata/savedgames/stalker - autosave.scop` (1.5 MiB, SHA-256 `65ca7458dbf8fecf0e2f050edb3b8d61e77098c1ccdcb61e46f191d3e2ce26f8`) and `.scoc` (268 KiB, SHA-256 `170f9477b42603443cc69656edb3b8d61e77098c1ccdcb61e46f191d3e2ce26f`). The earlier `newgame-silo` Silo run successfully loaded its own `player - autosave.scop` and completed (`exit-status.txt` is zero); its sampled state was `l01_escape`, calendar `2018-10-26 08:07:45`, weather `w_cloudy2_dark`, Device clock 1, game factor 6. That is the best already-present Windows-origin save candidate found within the bounded savedgames inspection. No corresponding `.dds` was present in that directory. I did not inspect direct user-install save directories or search other large roots.

For both failed runs, the likely first correction is the load route: `-load` is issued too early for this Windows binary. The code path in `src/xrGame/console_commands.cpp:1276-1303` validates a save and, before ALife exists, queues `start server(<save>/single/alife/load)`. Do not treat the existing attempts as save-load compatibility evidence until the Windows log confirms the requested save name was loaded and no `Creating new game...` path was taken. No runtime was changed and no game or build was run for this audit.
