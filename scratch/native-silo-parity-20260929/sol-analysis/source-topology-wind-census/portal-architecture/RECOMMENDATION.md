# Native Metal portal visibility: smallest safe integration shape

## Recommendation

Choose a renderer-owned, CPU-only topology snapshot (option B), populated from the active level load inputs, with a source-faithful portal walker. Keep its graph and frame result value-only: sector/portal indices, bounds, and visible-sector frusta; no `CSector*`, `CPortal*`, `dxRender_Visual*`, or ownership of the engine CDB. Start with observe-only admission for the main-view static/Flora G-buffer draws. Any missing input or uncertain geometry means keep the draw. Do not put the Metal path through legacy `LoadSectors` as-is.

This recommendation follows the current loader boundary: `CRender::level_Load`'s Metal branch loads lights and calls `LoadLevelScene`, then returns before the regular R4 path loads `Visuals`, `Details`, or `LoadSectors` (`src/Layers/xrRenderPC_R4/r4_loader.cpp:31-59, 108-142`). The regular path's `CSector::load` resolves a root with `getVisual(fs.r_u32())` (`src/Layers/xrRender/r__sector.cpp:262-284`), so calling `LoadSectors` alone is not a metadata bootstrap; it assumes the full legacy `Visuals` array and the lifetime of those render-owned objects. `LoadVisuals` constructs each `dxRender_Visual` and calls `V->Load` (`src/Layers/xrRenderPC_R4/r4_loader.cpp:330-348`), crossing into legacy visual/resource loading which this Metal route intentionally bypasses.

## A vs B

| | A. Legacy `LoadSectors` / root metadata bootstrap | B. Renderer-owned CPU graph |
|---|---|---|
| Reuse | Reuse `CSector`/`CPortal`, portal CDB construction, and `detectLastSector`; however `LoadSectors`' sector records resolve root IDs via `getVisual`, and the source traversal writes into `CDSGraphManager` internals. A real CPU-only version still needs a separate metadata root reader and a decoupled traversal result. | Reuse source binary contracts and math, but store simple copied records. One dedicated walker mirrors portal ordering, plane orientation, SSA/fade, clipping, visited-portal sets per sector, and multiple frusta without importing renderer-owned sector or graph-manager state. |
| Ownership/lifetime | Risky: `CRender` owns `Sectors`, `Portals`, `rmPortals`, `Visuals`; unload deletes them. `MetalRenderDeviceRender` separately resets the Metal scene on unload/reload (`MetalRenderDeviceRender.mm:604-617`). Any cross-retained source pointers can go stale or silently refer to a later level. | Clear: snapshot built for one level generation; it contains no engine pointers and is reset with `MetalR4EngineScene`. Tag the result with that generation and the active source receipt. |
| Provenance | `LoadSectors(IReader*)` sees the winning `level` reader, but existing Metal `LoadLevelScene` gets only `FS.get_path("$level$")->m_Path`; `R4LevelGeometry.cpp:868-871` reads `level` and `level.geom` as direct files. A mixed archive/loose-file view is possible unless inputs are explicitly joined. | At the `CRender::level_Load(IReader* fs)` boundary, copy the exact winning `fsL_SECTORS` / `fsL_PORTALS` chunks. Reuse the already-live `g_pGameLevel->ObjectSpace` CFORM model/tris/verts for start-sector rays, and carry the `level`/`level.geom` receipts alongside parsed OGF topology. Fail open if generation or receipt mismatches. |
| Scope to make it safe | Larger than it sounds: must avoid `getVisual`, supply root bounds, keep source sector arrays and renderer graph mutation coherent, and prove reset ordering. | Narrow data contract and deterministic teardown. Additional source parsing is contained behind one helper and one scene-owned snapshot; no cook or GPU path involved. |

So option B is the smaller *safe* ownership boundary, although option A appears shorter if it is described only as calling `LoadSectors`.

## Exact inputs/data the graph needs

1. **Topology from the winning level reader:** sector index; root visual ID; that sector's portal-ID list; for each portal, front/back sector IDs and its ordered 3–6 source vertices. The R4 loader's `b_portal` is two `u16` sector IDs plus an `svector<Fvector,6>`; sector chunks contain portal IDs and a root visual ID (`r4_loader.cpp:357-405`, `CSector::load` at `r__sector.cpp:262-284`). Validate every count/reference before graph use.
2. **Root bounds and descendant ownership:** `detectLastSector` first ray-tests the portal model, chooses the facing sector, and accepts it only when that sector's root visual bbox contains the eye; it then falls through to a sector-tagged CFORM hit (`r__sector_detect.cpp:50-84`). The legacy outdoor-sector heuristic also chooses the largest root-box volume (`r4_loader.cpp:430-445`). A Metal topology parser must read the root OGF header bounds and linked-child hierarchy. `R4LevelGeometry` already parses node type, shader ID, linked children, transforms, and static leaves, and provides `CollectR4StaticVisualDescendants`, but it does **not** retain OGF root bounds today (`R4LevelGeometry.cpp:594-639, 758-825`). Root bbox is required to exactly mirror portal-first start detection and the outdoor fallback; do not substitute root-volume heuristics for the start ray.
3. **Start-sector source data:** live `level.cform` is the game's built `CObjectSpace` static CDB; `detectLastSector` uses a nearest downward ray, retries upward only if no hit, and reads `TRI::sector` from the returned triangle (`r__sector_detect.cpp:50-84`; `src/xrCDB/xrCDB.h` sector tag). If exact portal-first behavior is required, build an independent CPU portal triangle query with source dummy-to-portal mapping first, then use the same nearest-hit and facing/root-box rules; otherwise keep the static CDB result for this captured no-portal-ray case only. Do not retain pointers into CObjectSpace across unload.
4. **Exact primary-view frame:** eye, view, projection/full transform, engine frame, and `Device.ViewportNear`; source portal construction derives the far plane from `Device.mFullTransform`, uses `Device.vCameraPosition`, and chooses the near-camera dual-render branch with `VIEWPORT_NEAR + EPS_L` (`r__sector.cpp:86-96,145-146,176-183`). `MetalRenderDeviceRender::SetCacheXform` currently copies view/projection/eye/frame (`MetalRenderDeviceRender.mm:1730-1747`) but not `ViewportNear` or a primary-camera source tag. A source-frame capture must occur at an unambiguous primary-view boundary and include exact near value; a saved `user.ltx`/launch setting is not a substitute. Do not use shadow face, scope, HUD, stale, or invalid view state. If the primary source cannot be proven for that frame, return no visibility result.
5. **Static draw mapping and conservative bounds:** current Metal static/Flora draws are selected from `level.geom` visual IDs and have per-visual indexed bounds; hierarchy mapping must assign each draw to every sector root that owns it (overlapping roots are possible). For wind-animated trees, portal/frustum admission must use a proven current-motion envelope over indexed rest geometry, not only the rest AABB/sphere. Current frame-700 work has exact geometry envelopes for 5,301 IDs and fails open on 15 uncertain bender cases; future runtime use still needs a temporal/current-array qualification before any cull.

The previous source screen anchors the archive-winning artifacts used for this ROI: `level` SHA-256 `1800a451d0bba9af1da69fae8683b36b6e6346709c0d6b9bf14385f4a48d19f7`; `level.geom` `a4552d34eec6f87ed7eb461327c8a331d1f7a3b9911a2b51342ca4d377f8d78a`; `level.cform` `6a8e56d483d60da0f461fb2e20ca64ba193b94ed883013c337c7d293a2410e31`. They must remain runtime receipts, not hard-coded general asset identity.

## Frame result and fail-open rules

The walker should emit `visibleSector -> vector<frustum>` with source-equivalent multiple-frustum semantics, plus a validity/generation bit and reasons. Mirror `CSector::traverse` and `CreateFrustumFromPortal`, including: initial frustum, portal sphere test, viewer-facing/back-side neighbor selection, start/current/visited-sector checks, SSA hard discard and optional LOD-B behavior, clipped polygon, near/far portal planes, cycle keying per sector, and all reached frusta. HOM is a distinct optional input and is **off** for the accepted ROI; a no-HOM result is a visibility superset. Unimplemented >6-vertex simplification or any malformed/degenerate portal must fail open by preserving the incoming frustum / disabling all portal culling for the frame, never by dropping a sector.

Only after observe-only diffing should one experimental consumer skip a main G-buffer static/Flora draw when its entire conservative animated envelope is outside **every** frustum of **every** owning sector. A missing owner, missing root bounds, parse/ref receipt mismatch, unknown wind state, invalid view, stale frame, math uncertainty, or graph failure means retain it. Keep normal camera clip culling and draw order as-is for non-rejected draws.

## Other work and boundaries

A valid sector/frustum graph could later help trim camera-only dynamic and local-light work, but it does not currently provide that by itself. `CDSGraphManager`'s source light path uses `light::get_sectors` / `has_light_visible_from_sectors` and source light-volume-vs-portal sector sets (`src/Layers/xrRender/light.cpp:262-294`); the Metal `R4EngineLocalLight` bridge currently carries ID, position, range, camera distance, and flags but no owning-sector/frustum key (`src/Layers/xrRenderMetal/IR4Backend.h:528-565`). Dynamic-world submissions carry world transform and sphere bounds but do not expose a sector key in the copied `R4EngineWorldRenderable` contract (`MetalRenderDeviceRender.mm:1218-1244`). Therefore a follow-on needs explicit conservative sector membership and should be measured separately; no implied current light/dynamic ROI is established.

The graph can at most filter **camera-visible** preparation. It must not suppress sun/local shadow casters: their light-space frusta can include geometry outside all primary camera portals. Do not gate shadow passes, shadow atlas batches, or caster prewarm with primary-view sectors without a separate light-frustum proof. HUD, scopes, and other auxiliary camera passes also remain outside this graph.

Existing same-binary result supplied for this decision: fixed-camera portal upper-bound ON improved `OnGlass` 25.8471→30.7889 (+19.12%) and CPU encode 34.4871→28.4542 ms, skipping 4,086 and keeping 1,230 Flora IDs. This supports a small ROI experiment; it is an upper-bound fixed-camera result, not quality, temporal-wind, general-level, or shipping-cull qualification.

## Smallest next experiment

1. Add only the CPU snapshot/parser and graph-result observation to the native renderer-owned scene, sourced from the active `fs` plus the active CFORM query API; leave all consumers drawing.
2. For one captured main frame, log primary camera provenance (`eye/view/projection/fullTransform`, `ViewportNear`, frame/pass), source asset generation/receipts, detected start sector, graph sectors/frustum counts, and per-ID owner + conservative envelope visibility. Compare IDs to the pinned 4,086 set only as a fixture check.
3. Require exact start sector 25 and expected no-HOM visible-sector/frustum result for the pinned fixture, zero false negatives against current clip-visible indexed geometry envelope audit, fail-open on every invalid source/input, and source restoration/updateability review.
4. Only then test a separate opt-in main-G-buffer skip on those graph-proven IDs, with image/motion checks at varied camera frames. Shadows, HUD, light capture and dynamic prewarm remain unchanged until separately instrumented and proven.

No source, build, cook, or game files were modified for this architecture screen.
