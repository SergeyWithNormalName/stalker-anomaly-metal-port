# Non-Flora main-scene portal opportunity triage

## Conclusion

LMH is the best next family for a small offline opportunity census. Its production G-buffer loop already uses the same dense source `visualId` as the prepared level geometry and texture-material map; each admitted material retains the exact indexed-position bounds and model transform used for the ordinary camera clip. The level-generation portal metadata maps every visual node to all sectors whose roots contain it. This gives a trustworthy source-ID/owner join without adding identity fields or rebuilding an engine/game path.

The census is feasible from existing parser and observer code, but this review did not run it. The current run’s LMH count (`submitted=1147`) is a local telemetry sample index, not an engine-frame receipt. The `active-frame700-per-id.csv` is specifically a 5,316-row Flora join; it cannot be reused as a general static-family visual-ID census. The fast-on run has matching active level bytes (SHA-256 `1800a451d0bba9af1da69fae8683b36b6e6346709c0d6b9bf14385f4a48d19f7`) and matching level geometry bytes (SHA-256 `a4552d34eec6f87ed7eb461327c8a331d1f7a3b9911a2b51342ca4d377f8d78a`) from the prior source receipts, but the saved per-frame output does not include full current view/projection bits or a per-family draw-ID list. Do not turn the current aggregate count into an exact LMH skip estimate without those frame inputs.

## Source identity and bound audit

- `R4LevelGeometry.cpp` assigns each parsed visual its chunk ID and validates IDs are dense and sequential. `R4StaticVisual.visualId` and `R4VisualNode.visualId` therefore address the same node/owner index. Its position-bounds routine walks every referenced index, validates the local index, reads the referenced `POSITION0` float3, and computes min/max from the actual indexed vertices.
- The prepared portal metadata walks each sector root’s linked-child hierarchy and appends that sector to each visual’s owner list. A visual with multiple sector roots therefore keeps multiple owners; an unowned or invalid record must remain visible. `R4PortalGraphResult` owns the reached per-sector `CFrustum` lists and raw visibility vector for the full parsed visual-node population.
- LMH’s `drawLevelScene` iterates `scene.geometry.visuals` in source order, then uses `textureMaterialByVisual[visual.visualId]`. `TextureMaterial` stores `visualId`, `localPositionBounds`, and `modelTransform`; material preparation copies bounds and transform from the same `R4StaticVisual`. The normal camera-frustum check occurs before drawing. A portal opportunity test can therefore start from exactly the LMH records that survive that ordinary clip.
- Terrain is also structurally joinable: `TerrainDraw` retains its `visualId`, indexed-position bounds, and model transform. `makeTerrainDraw` derives them from the same `R4StaticVisual`; terrain is a plausible second census family, but its current submitted counter is smaller than LMH’s.
- Def-vertex is joinable because its prepared `Draw` retains `visualId`, bounds, and model transform. Def-objects-LOD and static-forward prepared `Draw` records discard `visualId`; a census would have to reconstruct their exact classifier-selected rows from `R4LevelGeometry` and match source ranges/material admission. Their reported submitted counts are smaller, so they are not the first target.

## Cheap offline LMH census

1. Use the already captured active `level` bytes plus the winning `level.geom` bytes and run the existing `ParseR4LevelGeometry` / prepared portal-graph path. Require the exact level and geometry hashes above, `portalMetadata.available`, and a valid generation. Do not use the Flora-only CSV as the draw inventory.
2. Reconstruct the LMH candidate IDs from the same per-visual prepared source: valid source static visuals, valid POSITION bounds/pipeline, and IDs present in the prepared `textureMaterialByVisual` set. The runtime LMH loop’s one-visual/one-draw order provides a cross-check; record shader/alpha class and geometry ranges with each ID.
3. Reuse the prepared graph’s `reached` CFrustum lists, not a new portal formula. Require exact frame view/projection/full-transform/eye/near/SSA inputs. For every ordinary-camera-visible LMH draw, transform its indexed local AABB’s eight corners by its prepared model transform, construct a conservative world AABB/sphere, and test that geometry against every frustum for every owner sector. Exclude only if all owner/frustum tests reject. Missing owners, malformed/unknown bounds, unmatched IDs, or invalid graph input keep the draw.
4. Emit a per-visual CSV with `visualId`, shader/family, owner-sector list, existing-camera-clip result, tested owner-frusta, graph result, and reason. Cross-check total prepared/admitted IDs and post-camera count against the same source list. Report only an upper-bound eligible count; do not infer equivalent Windows draw counts, image quality, or frame-time savings.

A correct per-family frame census still needs a same-frame graph input receipt. The existing captured frame-700 full C++ replay is a possible offline source only after its view/projection bits are proven identical to the run window; the phase CSV’s position/direction alone is insufficient for that gate. If that bit match is unavailable, the census should use an already saved observer input from the measurement run or stop short of an exact opportunity number—no new game run is needed to settle source identity, but it may be needed to capture missing frame inputs in a future measurement.

## Size hints, not aligned counts

The fast-on engine log reports LMH `submitted=1147`, terrain `submitted=428`, def-vertex `submitted=449`, static-forward `submitted=68`, and def-objects-LOD `submitted=27`. Those source counters use different local sample indices and are not aligned as one frame. They only justify choosing LMH as the first family to census, not a relative CPU/GPU ranking. The portal graph’s own summary is about all source visual nodes and does not itself prove the number of LMH draws that would be rejected.

No CPU parser, graph replay, build, or game was run for this report. It adds no suppression or runtime code.
