# Existing runtime retry and CPU skin hooks

## Production frame lifecycle

- `XRAY_METAL_TEMPORAL_LIFECYCLE_PROBE=1` activates a real render-device lifecycle exercise in `MetalRenderDeviceRender::Begin`. Once a prepared gameplay scene has reached five begin ticks it sets `XRAY_METAL_TEMPORAL_FORCE_ACQUIRE_RETRY=1`; `MetalR4Backend::BeginFrame` consumes it, returns `Retry`, and releases the acquired slot semaphore before `beginAcquiredContext`. The next engine `Begin` reacquires normally. The same runtime probe reloads the level at tick 10 and resizes/restores the drawable at ticks 25/30, invalidating scene history around those lifecycle changes. This is an existing real runtime harness, not a registered CTest.
- A real late-submit retry can also be forced by setting `XRAY_METAL_E08_FORCE_SUBMIT_RETRY=<engine-frame>`. It is active when late drawable acquisition is in use (`XRAY_METAL_E08_EARLY_DRAWABLE` unset, which is the default). `SubmitFrame` abandons the encoded frame and reports `LastFrameSubmitWasRetry`; the render-device path calls `scene.DiscardUnsubmittedFrame()` and backend discard, then permits the next frame. The temporal lifecycle probe itself does not set this submit-retry flag; combine them explicitly for V5 runtime validation.
- The production scene already calls dynamic-world `Prewarm` while preparing gameplay, commits it through `OnFrameSubmitted` after successful `SubmitFrame`, and discards pending state when submit/retry fails. The adapter clears pending motion and advances its prewarm invocation epoch at the next `Prewarm`. This proves current dynamic-world/object-motion transaction wiring, but there is no production compute-skin output cache yet to prove.

## CPU skin diagnostics and their limits

- `XRAY_METAL_E07_FRAMES=<csv>` enables bounded per-frame and per-object records. Existing E07 timers/counters cover CPU `Repack`, skinned-bounds validation, upload time/bytes, computed/submitted/shadow vertex counts, pose reuse, cache hits/misses, and draw counts. This is the strongest existing live CPU-skin economics hook. It is diagnostic overhead and must stay off for ordinary timing windows.
- `XRAY_METAL_DYNAMIC_DRAW_DIAGNOSTICS=1` additionally repacks CPU vertices for per-draw finite-position/UV/clip-w diagnostics. It emits `METAL_DYNAMIC_CPU_VERTEX_DIAGNOSTIC` and can confirm the CPU reference stream for a live object. It duplicates work, so it is correctness diagnosis only.
- `XRay.Metal.DynamicWorldPreparedStateProbe` tests the shared prepared-state/epoch helper, including same-engine-frame retry, slot wrap, invalid pose, early/late Prewarm failures, and shadow-only disposition. It is CPU-only and does not call production `BeginFrame`, `Prewarm`, `SubmitFrame`, or commit/discard methods.
- The accepted `ComputeSkinBackendGpuProbe` is a separate offscreen Metal API test. It manually begins an internal acquired context, invokes production `EncodeComputeSkinJobs`, and validates GPU readback/stale spans/shared epochs. It does not force the real drawable retry or call `SubmitFrame`; keep that limitation explicit.

For a future V5 run, combine the existing temporal lifecycle flag with an explicit `XRAY_METAL_E08_FORCE_SUBMIT_RETRY` frame, keep `XRAY_METAL_E07_FRAMES` on only during the short correctness pass, and verify the run logs contain acquire retry, submit retry, subsequent successful submission, E07 skin counters, and fresh-prewarm output. Then repeat a separate timing pass with all diagnostics off. This harness cannot run until the Mac is manually unlocked; the one fresh read-only CUA check still reported it locked.

## CPU economics screen

The one bounded CPU-only screen uses the 30 installed leaves already qualified for GPU comparison (82,530 vertices); it skips the one existing CPU-fallback leaf. File extraction and canonical preparation happen before timing. The old call uses actual `RepackR4DynamicWorldSkinnedVertices` on the same installed bytes and deterministic bone palette; the new call uses `CheckR4ComputeSkinBounds` on that decoded canonical data. Per-influence median ns/vertex old vs new: 1W 33.21 vs 12.44, 2W 45.28 vs 12.39, 3W 53.25 vs 13.72, 4W 61.02 vs 15.11. This is conditional CPU laboratory work per vertex, not FPS or net integration economics. Exact argv, outputs, anti-optimizer checksum, and input/app hashes are under `cpu-economics/`.
